## 一、现在就做：建三个文件

先写游戏的「顶」。这份骨架**编译得过、也链接得过**，只是里面是个空循环——
所以给它加了 60 帧上限，跑一下能正常退出。注释里那些「缺 X」就是接下来要补的东西。

```cpp
// src/main.cpp
#include "game/Game.h"
int main(int argc, char** argv) {
    game::Game g;
    return g.run(argc, argv);
}
```

```cpp
// include/game/Game.h
#pragma once
namespace platform { class Window; class Input; }
namespace world    { class TileMap; class Camera; }
namespace gfx      { class Renderer; }
namespace ecs      { class Registry; }

namespace game {
class Game {
public:
    int run(int argc, char** argv);
private:
    void update(float dt);
    void render();
    bool running_ = false;
};
}
```

```cpp
// src/game/Game.cpp
#include "game/Game.h"

int game::Game::run(int, char**) {
    // ① 开窗口              → 缺 Window
    // ② 载入地图 / 素材      → 缺 TileMap、Atlas
    running_ = true;
    for (int frame = 0; running_ && frame < 60; ++frame) {  // 临时上限：没窗口前别空转
        // ③ 读输入           → 缺 Input、Clock
        update(1.0f / 60.0f); // ④ 缺 Registry、Collision、Camera
        render();             // ⑤ 缺 Renderer、Blitter、Surface
        // ⑥ 上屏             → 缺 Window::present
    }
    return 0;
}
void game::Game::update(float) {}
void game::Game::render()      {}
```

**下一步只有一个动作**：把 ① 那行注释变成真代码（`platform::Window win;`）。
写到这一刻才会真的缺东西，然后按第三节的表去补。

## 二、动手前先看清整体（10 分钟）

### 一帧在干什么

**读输入 → 改世界 → 画出来 → 上屏**。展开：

```
main()
└─ Game::run()                         唯一的主循环
   ├─ Input::poll()                    键盘 → 当前帧 / 上一帧
   ├─ Game::update(dt)
   │   ├─ PlayerSystem                意图 → Transform / HitBox
   │   ├─ MovementSystem              位置 += v*dt，撞墙回退
   │   ├─ AISystem · Quest · Dialog   敌人、旗标、门禁
   │   └─ Camera::follow(player)
   ├─ Game::render()
   │   ├─ Renderer::draw_map          地图 + 相机 → 可见 tile
   │   ├─ Renderer::draw_entities     Registry → 按 y 排序
   │   ├─ Renderer::draw_weather / draw_ui
   │   └─ Blitter                     所有请求最终落到像素混合
   └─ Window::present(framebuffer)    SDL 上屏
```

### 模块之间是什么关系

三件事，别混：

1. **编译依赖**：箭头只能朝下（`core` 不认识 `gfx`，`gfx` 不认识 `game`）。分层图见 `01`。
2. **运行时数据流**：上面那张调用图。
3. **所有权**：只有 `Game` **拥有** `Window`/`Atlas`/`TileMap`/`Registry`/`Renderer`；`Renderer` 只借用 `TileMap&`，`Blitter` 只收一块 `Surface&`。所以换地图只改 `Game` 手里那一个对象。

九个模块一句话：`main` 启动 → `game/Game` 编排一帧 → `platform` 唯一碰 SDL → `world` 存地图和查询 → `ecs` 管场上实体 → `gfx/Renderer` 把"画什么"变成"往哪写" → `gfx/Blitter` + `simd` 唯一做像素混合 → `core` 是所有人都能用、谁都不认识的基础类型 → `ui` 是最后才需要的编辑器。

### 只锁三条接口

其余一律前向声明 + 桩，防止接口反复返工：

```cpp
Window::present(const Surface& fb);                    // 怎么上屏
Renderer::sprite(const Surface&, Rect src, int x, int y); // 怎么画一张
TileMap::at(int tx, int ty) const -> int;              // 怎么读世界
```

## 三、卡到哪，补到哪

**不要再按阶段号往下做。** 看编译错误、链接错误，或者"编译过了但屏幕是空的"。

| 你卡在哪 | 缺什么 | 去哪一册抄完整文件 | 补完屏幕会多出 |
|---|---|---|---|
| ① 开窗口 | `Window` | `03a` 阶段 0 | 黑窗口 |
| ⑥ `present` 要像素缓冲 | `Types.h`、`Surface` | `03a` 阶段 1 | 纯色清屏 |
| ② 载入 PNG | `Atlas` | `03a` 阶段 2 | 图进内存 |
| ⑤ 要往 fb 写像素 | `Blitter`（**先只写标量**） | `03a` 阶段 3 | **第一张精灵** |
| 精灵能画了，慢 / 想学 | `simd/*` + `02` 前半 | `03a` 阶段 4 | 画面不变，帧率变 |
| 想显示整张地图 | `TileMap`、`Camera` | `03b` 阶段 5–6 | 地图、滚屏 |
| WASD 没反应 / 穿墙 | `Input`、`Collision`、`Animator` | `03b` 阶段 7–8 | 能走、撞不进树 |
| 要几十个敌人、能打 | `Registry`、战斗与 AI | `03b` 9、`03c` 10–11 | 能打、能被打 |
| 对话、天气、血条、Boss | 内容与表现 | `03d` 12–16 | 完整一局 |
| `Game` 太大要收拢 | 正式版 `Game.h/.cpp` | `03e` 17–23 | 结构稳定 |
| 想不重启改地图 | F2 编辑器、热重载 | `03g` 24 | 实时编辑器 |

完整文件一律从 `03a`–`03g` **整块粘**，自己写的桩别留到最后。
`03f` 只在"文件建多了编译报错"时查——它管的是**编译顺序**，不是阅读顺序。

## 四、每一轮都长这样

```
写上层 → 卡住 → 记下确切的失败 → 只补够用的最小接口 → 回上层继续 → 说清屏幕多了什么
```

最后一步不能省。一堆能编译的桩不是进度。

第一次碰到 `blit_alpha` 只写标量版；`tinted / mask / stretch` 等天气、字体、怪物尺寸差异真正出现时再一个个加。

## 附录：为什么这么排（不想看可以跳过）

旧讲义按**依赖顺序**排（阶段 0 窗口 → 4 SIMD → 17 Game → 20 main），编译上无懈可击，但不是人写代码的顺序。区别不在"顺序反过来"，而在驱动力：旧的是**阶段表**决定下一步，这里由**卡点**决定下一步。

代价要认：接口会返工 2–3 次（靠三条契约 + 前向声明收敛）；桩会制造进度幻觉（靠每轮绑定可见产物）；急着让画面出来时没心思推 `div255`（靠 `02` 拆两次读）；半文件带桩的写法与"整块粘贴"有摩擦（本册只回答"何时需要什么"，落盘一律用完整代码块）；错误来源变宽（一次只补一个模块，补完立刻编译）。
